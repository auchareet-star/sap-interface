การเชื่อมต่อ HIS ⇄ SAP ERP

เอกสารนี้อธิบายว่าระบบ HIS ส่งและรับข้อมูลกับ SAP ที่จุดไหนบ้าง ใช้เทคโนโลยีอะไร และการกระทำของผู้ใช้แต่ละอย่างทำให้เกิดอะไรขึ้นอีกฝั่ง สำหรับทีม ERP, ทีม IT และผู้เกี่ยวข้องที่กำลังจะทำ Interface SAP ในโปรเจคถัดไป

ประกอบกับเอกสาร: SDA-SAP Interface Spec V.1.0.0, FS/TS ฝั่ง SAP, Solution โยธี–จักรี (28 ม.ค. 2026) จัดทำ: 19 ก.ย. 2026

01สรุปสำหรับผู้บริหาร

ระบบโรงพยาบาล (HIS) กับระบบบริหารทรัพยากรของมหาวิทยาลัย (SAP) เป็นคนละระบบและคนละฐานข้อมูล แต่พูดถึงเงินและของชิ้นเดียวกัน Interface คือสะพานที่ทำให้ข้อมูลไหลถึงกันโดยไม่ต้องคีย์ซ้ำ — เงินที่รับหน้าเคาน์เตอร์กลายเป็นรายการบัญชีใน SAP ของที่เบิกจากคลังใหญ่ไปตัดสต็อกให้ถูกทั้งสองระบบ และข้อมูลหลักอย่างรายการยา ผู้ขาย ศูนย์ต้นทุน ถูกสร้างที่ SAP ที่เดียวแล้วกระจายมาให้ HIS ใช้

สิ่งที่ต้องรู้ในระดับบริหารมี 3 ข้อ: (1) ข้อมูลส่วนใหญ่ไหลทางเดียว HIS ส่งธุรกรรมไป SAP และ SAP ส่งข้อมูลหลักกลับมา (2) การลงบัญชีไม่ได้เกิดอัตโนมัติ ต้องมีคนกดส่งหลังตรวจสอบ ซึ่งเป็นจุดควบคุมที่ตั้งใจออกแบบไว้ และ (3) ถ้าระบบกลางหรือ SAP ใช้งานไม่ได้ งานคลังพัสดุบางอย่างจะทำต่อไม่ได้จนกว่าจะกลับมา

14 เส้น interface

HIS → SAP 6 เส้น (GLI01, MMI01, MMI02, MMI02-Dispensing, MMI03, MMI04) และ SAP → HIS 8 เส้น (HRO01, MMO01–03, AP01, FM01, CO01, CO02)

SOAP Web Service

ทุกเส้นใช้ SOAP 1.1 ฝั่ง SAP เปิด Web Service (Y* function) ให้เรียก และ SAP เรียกกลับเข้ามาผ่าน SOAP ไม่มีการใช้ไฟล์หรือ RFC ตรง

4 ระบบในเส้นทาง

SAP ⇄ Interface App ⇄ SAP Broker ⇄ HIS — HIS ไม่ต่อ SAP โดยตรง และ Broker ของเราก็ไม่ต่อ SAP โดยตรง ทุกข้อความผ่าน Interface App ของ Vendor SAP

Real-time + batch 1 เส้น

ส่วนใหญ่เป็นแบบ synchronous — ผู้ใช้กดแล้วรอผล SAP ทันที ยกเว้นการจ่ายยาผู้ป่วยที่ส่งแบบ batch job

ศัพท์พื้นฐานก่อนอ่าน

Interfaceเส้นทางส่งข้อมูลอัตโนมัติระหว่างสองระบบ หนึ่ง "เส้น" คือข้อมูลหนึ่งชนิดที่ตกลงรูปแบบกันไว้แล้ว เช่น เส้นส่งรายการบัญชี เส้นส่งข้อมูลยา
Master Data
vs Transaction		Master data คือข้อมูลหลักที่เปลี่ยนไม่บ่อย (รายการยา ผู้ขาย ศูนย์ต้นทุน บุคลากร) · Transaction คือรายการที่เกิดทุกวัน (ใบเสร็จ ใบเบิก การจ่ายยา) — คนละจังหวะและคนละความเร่งด่วน
Real-time
vs Batch		Real-time ส่งทันทีที่เกิดเหตุและรอคำตอบ · Batch รวบรวมไว้แล้วส่งเป็นรอบ (ในระบบนี้ใช้กับการจ่ายยาผู้ป่วยที่มีปริมาณมาก)
ตัวกลาง
(Middleware)		โปรแกรมที่คั่นกลางไม่ให้สองระบบผูกติดกันโดยตรง ทำหน้าที่แปลงรูปแบบข้อความ เลือกปลายทาง และเก็บบันทึก ในระบบนี้มีสองตัวคือ Interface App และ SAP Broker
SOAP / WSDLSOAP คือรูปแบบข้อความมาตรฐานแบบ XML ที่ SAP ใช้คุยกับระบบอื่น · WSDL คือไฟล์ "สัญญา" ที่บอกว่าบริการนั้นรับ-ส่งข้อมูลอะไรบ้าง อีกฝั่งเอาไปสร้างโปรแกรมเรียกใช้ได้ทันที
REST / JSONรูปแบบข้อความยุคใหม่ที่เบากว่าและอ่านง่ายกว่า SOAP ใช้ระหว่าง HIS กับ SAP Broker ส่วน Broker เป็นคนแปลงเป็น SOAP ให้ฝั่ง SAP
Endpointที่อยู่ปลายทาง (URL) ที่ใช้ส่งข้อความไปหาอีกระบบ
Posting Ruleตารางใน SAP ที่แปลง "รหัสประเภทธุรกรรม" ที่ HIS ส่งมา ให้กลายเป็นเลขบัญชีและประเภทเอกสาร ทำให้เปลี่ยนผังบัญชีได้โดยไม่ต้องแก้ HIS

ภาพรวมการไหลของข้อมูล

  • SAP เป็นเจ้าของ Master Data (วัสดุ/ยา, หน่วยนับ, ผู้ขาย, ศูนย์ต้นทุน, Internal Order, Functional Area, บุคลากร) → ส่งมาสร้าง/แก้ใน HIS อัตโนมัติ
  • HIS เป็นต้นทางของธุรกรรม — รายได้/ลูกหนี้ (ลงบัญชี FI), การเบิก-โอน-ตัดจ่ายคลังย่อย, การจ่ายยาผู้ป่วย, บิล Lab ทันตกรรม → ส่งไป SAP
  • SAP เป็นต้นทางของการเคลื่อนไหวคลังใหญ่ — การจ่ายของจากคลังใหญ่ให้คลังย่อย, รับของจาก PO, ยกเลิกรับ → ส่งกลับมาเพิ่ม/ลดสต็อกใน HIS
  • HIS ไม่ส่งเลขบัญชี GL — ส่งเฉพาะ "รหัสจำแนกธุรกรรม" แล้ว SAP แปลงเป็นบัญชีเองด้วยตาราง Posting Rule

02สถาปัตยกรรมการเชื่อมต่อ

SAP ตัวเดียวใช้ร่วมกันทั้งโยธีและจักรี ระหว่าง SAP กับ HIS มีตัวกลาง 2 ชั้น คือ Interface App (พัฒนาโดย Vendor SAP เป็นระบบเดียวที่ติดต่อ SAP) และ SAP Broker (พัฒนาโดย Ayodia เป็นตัวที่คุยกับ HIS ทุก site) รวมเป็น 4 ระบบในเส้นทางเดียว

HIS (HAOS.Main) — Ayodia

  • ระบบ HIS แยก instance/DB ต่อ site (โยธี, จักรี)
  • เรียก SAP Broker ด้วย HTTP POST JSON + header X-Broker-Key (ไม่รู้จัก Interface App และ SAP โดยตรง)
  • รับข้อมูลจาก Broker ที่ POST /api/sap-receive/{interfaceId}
  • เก็บ log ที่ TB_SAP_DATA_LOGS / …_DETAILS ดูได้ที่เมนู Admin › Log การเชื่อมต่อ SAP

SAP Broker (HAOS.Sap) — Ayodia

  • .NET 8 Web API แยก process, DB ของตัวเอง (HAOS_Sap_Broker)
  • ขาไป: แปลง JSON จาก HIS → SOAP ส่งให้ Interface App ผ่าน WCF proxy ที่ generate จาก WSDL
  • ขากลับ: เปิด SOAP endpoint (*.svc) รับข้อความ → log → route → fan-out ไป HIS แต่ละ site
  • ตอบกลับด้วย HTTP 200 + ตาราง ResponseData เสมอ (ไม่ส่ง SOAP Fault เพราะจะทำให้คิวขาออกฝั่ง SAP ค้าง)
  • ไม่เรียก SAP โดยตรง — ปลายทางที่ตั้งค่าไว้คือ Interface App

Interface App — Vendor SAP

  • พัฒนาและดูแลโดย Vendor ของ SAP อยู่ระหว่าง SAP กับ SAP Broker
  • เป็นระบบเดียวที่ติดต่อกับ SAP ทั้งขาเข้าและขาออก
  • รูปแบบข้อความ การตรวจสอบ และ log ภายใน เป็นไปตามที่ Vendor กำหนด
  • เป็นจุดตัดความรับผิดชอบ: ปัญหาหลังจุดนี้คุยกับทีม SAP ก่อนจุดนี้คุยกับ Ayodia

SAP (DT-ERP) — ทีม SAP

  • Inbound: RFC function module Y* เปิดเป็น Web Service ผ่าน SOAMANAGER ให้ Interface App เรียก
  • Outbound: user exit / BAdI ทำงานตอนผู้ใช้กด Save ใน T-code (เช่น MM01, MIGO, XK01) → ABAP Client Proxy เรียก SI_{ID}_IN ของ Broker แบบ real-time
  • บันทึกทุกรายการใน YTLOG และใช้กุญแจจาก HIS ตรวจซ้ำ ส่งซ้ำรายการที่สำเร็จแล้วจะถูกปฏิเสธ
  • แปลงรหัสจาก HIS เป็นบัญชี GL, Cost Center และ Internal Order ด้วยตาราง YTFIGL01_*
  • มีรายงาน Interface / Error ฝั่ง SAP (YINRP001, YINRP002)

ข้อตกลงเรื่องผลตอบกลับ (Response Convention)

HIS → SAP

  • SAP ตอบเป็นตาราง ExResponseData (GL ใช้ Tabout) แถวละ {DATE, TIME, SOURCE_KEY, FIELD, VALUE}
  • แถว FIELD = "Error" คือ error เชิงธุรกิจของรายการนั้น
  • batch ตอบผล รายบรรทัด → Broker สรุปเป็น SUCCESS / PARTIAL_SUCCESS / FAILED
  • ยกเลิก/กลับรายการ = ส่งเอกสารใหม่พร้อม flag (InversionFlg = "X", ImNomoreissue) ไม่มี API ลบ

SAP → HIS

  • Broker ตอบ SAP ด้วย HTTP 200 เสมอ พร้อม ResponseData {DATE, TIME, SOURCE_KEY, FIELD, VALUE}
  • ตารางว่าง = สำเร็จทั้งหมด · FIELD = "Error" = รายการที่ไม่ผ่าน · FIELD = "DocRequestNo" = เลขเอกสาร HIS ที่สร้าง (MMO03)
  • HIS ตอบ Broker เป็น HTTP 200 + {success:false, errors[…]} สำหรับ error ธุรกิจ
  • MMO03 ส่งซ้ำได้อย่างปลอดภัย — HIS ตอบ IRNO_DUPLICATE พร้อมเลขเอกสารเดิม

6.7 Error code ที่ต้องตกลงร่วมกัน

ถาวร (ส่งซ้ำก็ไม่ผ่าน ต้องแก้ข้อมูล)

  • VALIDATION_* — ข้อมูลไม่ครบ/ผิดรูปแบบ
  • LOOKUP_*_MISS — ไม่พบ master (พัสดุ, คลัง, แหล่งเงิน, หน่วยนับ)
  • DB_CONSTRAINT_* — ผิดกฎข้อมูลปลายทาง
  • PARENT_NOT_FOUND — อ้างใบเบิก/เอกสารต้นทางไม่เจอ
  • UNKNOWN_INTERFACE — ส่งมาผิดเส้น (ป้องกันการตอบรับเงียบ)

ชั่วคราว (ระบบ retry ให้)

  • TIMEOUT, DB_ERROR, INTERNAL_ERROR
  • HTTP 5xx, 408, 429 และ network error
  • HTTP 200 ที่ไม่มี field success → ถือเป็นชั่วคราว (UNRECOGNIZED_RESPONSE)

ข้อความ error ที่ส่งออกนอกระบบ

  • ข้อความเชิงธุรกิจส่งกลับตามจริง เพื่อให้ผู้ใช้แก้ได้
  • ข้อความระบบ (DB, internal, timeout) ถูกแทนด้วยข้อความกลางพร้อม CorrelationId ไม่ให้ชื่อตาราง/host หลุดออกไป

6.9 ขั้นตอนเปิด interface เส้นใหม่

  1. ตกลง ทิศทาง, trigger, ความถี่ และ business key ที่ใช้กันซ้ำ
  2. ทำ mapping sheet รายฟิลด์ (ชื่อ, ชนิด, ความยาว, บังคับ/ไม่บังคับ, ค่าที่เป็นไปได้, ที่มาในแต่ละระบบ)
  3. ฝั่ง SAP เปิด service แล้วส่ง WSDL ให้ → generate proxy ใน Broker → เพิ่ม mapping ชื่อฟังก์ชัน + endpoint config
  4. ถ้าเป็นขา SAP → HIS: เพิ่ม SOAP endpoint ใน Broker, เพิ่ม handler ที่ /api/sap-receive/{id} ของ HIS และ กำหนดฟิลด์ที่ใช้ route ไปแต่ละ site
  5. ตกลงรูปแบบ response และรายการ error code ก่อนเริ่มเขียน
  6. เตรียม test kit (ยิงตรงเข้าปลายทาง), simulator/mock และ scenario ครอบทุก movement type / transaction type
  7. ทดสอบเคสไม่สวย: partial fail, ส่งซ้ำ, timeout, master data ขาด, ข้อความเกินขนาด
  8. ก่อน go-live: ตรวจ log ครบทุกชั้น, ตั้ง monitor/alert, และตกลงช่องทางแจ้งปัญหาแต่ละช่วงของเส้นทาง

11Log, การจัดการ Error และการส่งซ้ำ

บันทึก (Log) มีทุกชั้น

  • HIS: TB_SAP_DATA_LOGS + รายบรรทัด — หน้า Admin › Log การเชื่อมต่อ SAP (อ่านอย่างเดียว)
  • Broker: TbSapTransactionLog เก็บ JSON และ SOAP XML ดิบทั้งขาไปขากลับ + ผลรายไซต์ — Dashboard ของ Broker มี export CSV
  • Interface App: log ตามที่ Vendor SAP จัดให้ (ต้องขอสิทธิ์เข้าดูหรือขอให้ทีม SAP ตรวจให้)
  • SAP: ตาราง YTLOG (สถานะ W/S/E) ดูผ่าน T-code YINRP001 (Interface) และ YINRP002 (System error)
  • ทุกธุรกรรมมี CorrelationId ใช้ตามรอยข้ามทั้ง 3 ชั้นได้

การส่งซ้ำ (Retry / Resend)

  • HIS → SAP ไม่มี retry อัตโนมัติ ผู้ใช้กดทำรายการเดิมซ้ำ ระบบข้ามบรรทัดที่สำเร็จแล้ว (Smart Resume)
  • SAP → HIS ถ้าบาง site สำเร็จ Broker retry site ที่เหลือแบบ backoff (30s → สูงสุด 5 ครั้ง) · ถ้าล้มเหลวทั้งหมด ต้องให้ SAP ส่งซ้ำหรือ admin กด retry รายไซต์
  • Dispensing job retry 3 รอบต่อรายการ
  • HIS รับข้อมูลซ้ำได้ (idempotent) ด้วยกุญแจ IRNO + รายการ

สถานะที่ต้องรู้

  • SUCCESS / PARTIAL_SUCCESS / FAILED — ผลรวมของ batch
  • Diverged — SAP รับบางบรรทัดแล้ว แต่ HIS rollback (ต้อง reconcile)
  • Dead letter — ครบจำนวน retry หรือเป็น error ถาวร
  • Broker มีรายงาน MMO03 gap: เอกสารที่ได้รับรายการไม่ครบตาม TOTAL_REC
ความเสี่ยงที่พบในโค้ด (ควรนำไปคุยร่วมกัน):
  • Timeout ไม่เท่ากัน: HIS รอ 15 วินาที แต่ Broker รอ SAP 30 วินาที ถ้า HIS หมดเวลาก่อน SAP อาจ post สำเร็จไปแล้ว SAP กันเอกสารซ้ำได้ด้วย SSBREF / IRNO ใน YTLOG แต่เมื่อผู้ใช้กดซ้ำ HIS จะเห็นเป็น error "has ever been created" ทั้งที่ SAP มีเอกสารแล้ว ต้องกระทบยอดด้วยมือ
  • เส้นทางมี 2 ตัวกลาง: เวลาที่ใช้และจุดที่พังเพิ่มขึ้นหนึ่งช่วง ต้องตกลง timeout ของแต่ละช่วงให้ลดหลั่นกัน และตกลงว่าจะตามรอยข้ามระบบด้วย key ใด (CorrelationId ของ Broker + SSBREF/IRNO ของธุรกรรม)
  • ผูกกับ transaction ของผู้ใช้: ถ้า SAP/Broker ล่ม ผู้ใช้จะอนุมัติใบเบิก โอน หรือยืม-คืนไม่ได้เลย เพราะยังไม่มี outbox/queue
  • ไม่มี API ยกเลิกใน SAP: บรรทัดที่ SAP รับไปก่อน HIS rollback จะค้างอยู่ใน SAP ต้องกระทบยอดด้วยมือ
  • SOAP endpoint ฝั่ง SAP → Broker ไม่มีการยืนยันตัวตน: อาศัยการจำกัดเครือข่ายอย่างเดียว
  • รูปแบบวันที่: ถ้า server ตั้ง locale เป็นไทย วันที่จะออกมาเป็นปี พ.ศ. ต้องใช้ InvariantCulture

B5จักรีใช้รหัสชุดแยก (_MS) เฉพาะฝั่งบัญชี หรือทุกเส้นเห็นชุดรหัสแยกเฉพาะในตาราง Posting Rule
B6รหัสที่ไม่มี interface (movement type, คลัง, แหล่งเงิน, หน่วยนับ, ประเภทวัสดุ) ใครเป็นเจ้าของ และตรวจความตรงกันเมื่อไหร่ตั้งค่าด้วยมือทั้งสองฝั่ง ถ้าไม่ตรงกันจะ error ตอนส่งจริง
B7ต้องการให้ HIS เห็นสถานะเอกสารใน SAP (PR/PO, การจ่ายเงิน, งบคงเหลือ) หรือไม่ยังไม่มีเส้นไหนส่งสถานะกลับ เป็นคำถามที่ผู้ใช้ถามบ่อยที่สุด

14บทเรียนสำหรับโปรเจคใหม่ที่จะเชื่อม SAP

สิ่งที่ควรตกลงกับทีม ERP ตั้งแต่ต้น จากประสบการณ์โปรเจคนี้

01

ตกลง "มุมมองทิศทาง" และชื่อ interface ให้เป็นชุดเดียว

โปรเจคนี้ใช้รหัสจากมุมมอง SAP (I = เข้า SAP, O = ออกจาก SAP) แต่เอกสารเดิมฝั่ง HIS ใช้เลขอีกชุด (เช่น MMI01 ของ SAP = MMO02 ในเอกสาร SSB เดิม และ service MMI03 ชื่อจริงคือ YSV_MMI07) จึงสับสนบ่อย ควรมีตารางชื่อเพียงตารางเดียวตั้งแต่วันแรก

02

เขียนแผนผังระบบและเจ้าของให้ชัดก่อนเริ่ม

เส้นทางจริงมี 4 ระบบ (SAP ⇄ Interface App ⇄ SAP Broker ⇄ HIS) และคนละบริษัทดูแลคนละช่วง ควรตกลงตั้งแต่ต้นว่าใครเปิด endpoint ให้ใคร ใครถือ credential ใครดู log ช่วงไหน และเวลามีปัญหาจะไล่จากช่วงไหนก่อน

03

ให้ SAP เป็นคนเลือกเลขบัญชี

HIS ส่งแค่รหัสจำแนก (Transaction/Line/HN/พันธกิจ/ช่องทางรับเงิน) แล้ว SAP แปลงด้วย Posting Rule การแก้ผังบัญชีจึงไม่กระทบ HIS แต่ต้องมีหน้าจอให้ผู้ใช้ดูแลรหัสทั้งสองฝั่งให้ตรงกัน

04

กำหนด business key ที่ SAP ใช้ตรวจซ้ำได้

ทุก interface ต้องมีกุญแจอ้างอิงที่ SAP echo กลับและใช้ตรวจซ้ำ (เช่น SSBREF, IRNO+ลำดับ) และตั้ง timeout ของ HIS ให้ยาวกว่าของตัวกลาง

05

เลือก sync หรือ async ให้เหมาะกับแต่ละเส้น

Query (ยอดคงเหลือ) ควร sync ส่วนการ post เอกสารควรพิจารณา outbox/queue เพื่อไม่ให้งานหน้างานหยุดเมื่อ SAP ล่ม ธุรกรรมปริมาณมาก (จ่ายยา) ใช้ batch

06

อย่าตอบ SOAP Fault กลับไปที่ SAP

ทีม SAP ยืนยัน (24 ก.ค. 2026) ว่าถ้าได้ Fault คิวขาออกฝั่ง SAP จะค้าง ให้ตอบ HTTP 200 พร้อมตาราง Error รายรายการแทน และทำให้ฝั่งรับรับข้อความซ้ำได้โดยไม่เกิดผลซ้ำ

07

ถ้ามีหลาย site ต้องมี field สำหรับ route ใน payload

SAP ใช้ร่วมแต่ HIS แยก จึงต้องมีค่าอย่าง Cost Center หรือ Storage Location ในข้อความ และกำหนดว่าจะทำอย่างไรเมื่อหาปลายทางไม่เจอ (โดยเฉพาะข้อมูลบุคคล)

08

Master data ที่ไม่มี interface ต้องมีเจ้าของ

Movement Type, Plant, Storage Location, หน่วยนับ, ประเภทวัสดุ ถูกตั้งด้วยมือทั้งสองฝั่ง ควรมีผู้รับผิดชอบและขั้นตอนตรวจความตรงกันก่อน go-live

09

เตรียมเครื่องมือทดสอบตั้งแต่ SIT

สิ่งที่ช่วยได้มาก: Test kit ยิง SOAP ตรงเข้า SAP, Simulator/Mock SAP ในตัวกลาง, ปุ่ม Preview payload เป็น Excel ให้ผู้ใช้ตรวจ และ scenario ทดสอบแยกตาม Movement Type / Transaction Type

10

วางแผน Reconcile และหน้าจอแก้ไขตั้งแต่ต้น

ควรมีรายงานยอดรวมรายวัน HIS เทียบ SAP และหน้าจอจัดการรายการค้าง (resend, mark resolved) ปัจจุบัน HIS มีแค่หน้าดู log

11

ความปลอดภัยของช่องทาง

กำหนด TLS, IP allowlist หรือ credential ให้ endpoint ที่ SAP เรียกเข้ามา และเก็บ user/password SAP กับ key ไว้นอก source code
